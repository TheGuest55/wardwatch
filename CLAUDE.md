## What we are building

A Docker testbed simulating a hospital ward talking over MQTT through Mosquitto: **4 beds**, each with a patient monitor, infusion pump and wearable (12 device streams), plus a nurse station (the only client allowed to send pump commands). An attacker container runs 8 scripted attacks and logs exact start/end times as ground truth. All traffic (including ARP) is captured, turned into features, and used to train and evaluate three ML model families, which feed a forensic triage layer and a dashboard.

**Threat model:** attacker is a machine on the ward network with no credentials. MQTT runs without TLS; the broker enforces per-device credentials and topic ACLs. The attacks follow a chain:
- Reconnaissance: network scan
- Disruption: SYN flood; MQTT connect/publish flood
- Credential access: broker brute-force; ARP-spoofing MITM that sniffs credentials in transit
- Abuse of stolen credentials: wildcard-subscription eavesdropping (nurse-station creds); spoofed vital signs (device creds); unauthorised pump commands (nurse-station creds)

Spoofed vitals and pump commands with stolen credentials are **expected to be the hardest classes**. That is a predicted finding, not a failure; report them separately.

**Data volume targets:** ≥ 6 h normal traffic, ≥ 5 runs per attack class, ≥ 5 capture sessions. The schedule must put every attack class in the train, validation **and** test sessions (cut-offs, calibration and thresholds are tuned on validation, so it needs attack data). Every attack, floods included, uses a **fixed source address** — no `--rand-source` (labelling and incident grouping depend on it).

Research questions:
- **RQ1** Which of three ML families (XGBoost, autoencoder, LSTM) best detects attacks: binary attack-vs-normal F1, false-positive rate, latency per 5-second host window?
- **RQ2** How much does detection degrade on unseen attack types and on a different network (our testbed vs CICIoMT2024)?
- **RQ3** Can the deployed detector pair run in real time and produce incidents that are correctly grouped, well calibrated and faithfully explained?

## Datasets

- **Ward testbed** (generated by us) — primary training/evaluation data.
- **CICIoMT2024**, Wi-Fi/MQTT subset only — cross-dataset test and benchmark against published results. Raw PCAPs with official train/test splits; downloaded on the host into `data/raw/ciciomt2024/`.
- **PhysioNet BIDMC** — real vital signs replayed as device payloads (realism only, not security data).

## Pipeline decisions (fixed — don't change without asking)

- **Features** — one extractor for both datasets (run it on CICIoMT2024 PCAPs too):
  - NFStream flow statistics;
  - MQTT: message type, payload size, per-client connect/publish rates, connections reusing an active client ID, **topic-derived** features (wildcard use, topic depth, is-command-topic). **Never the raw topic string** — it acts as an identifier;
  - payload plausibility: jump in each vital-sign value vs that device's recent readings (testbed only);
  - **layer 2**: ARP replies per window, IP→MAC mapping changes. NFStream ignores ARP, so this needs its own parser.
  - Cross-dataset experiments use only features both datasets can provide.
- **Granularity:** the unit for all model comparisons, latency and real-time scoring is **one row per host per 5-second window**. A host = any machine keyed by MAC address (devices, nurse station, broker, attacker); its row covers every packet it sends or receives in the window. Flow-level rows are a secondary analysis only.
- **Labels (testbed):** window = attack if it holds traffic from the attacker's IP **or MAC** inside that attack's logged interval. ARP spoofing is labelled **by MAC** (forwarded packets keep the victims' IPs). Drop windows straddling boundaries and count them. **CICIoMT2024:** use CIC's per-file attack labels; verify against its docs and log what you find.
- **Leakage control:** IPs, MACs, ports, client IDs, raw topics and timestamps are **never model inputs** (metadata for forensics only). Split by time, never random shuffle. Fit scalers/SMOTE/thresholds on train/validation only.
- **Models and roles:**
  - Classifiers: XGBoost (baseline Random Forest) · LSTM over a sequence of windows (baseline 1D CNN = stretch).
  - Anomaly detector: autoencoder trained on normal traffic only (baseline Isolation Forest).
  - Non-ML rule baseline: rate thresholds + wildcard-subscription rule.
- **Common metric:** **binary attack-vs-normal F1** for every model in every experiment. Multiclass macro-F1 (naming the type) for classifiers under Experiment A only — a withheld class can't be named.
- **Selection rule (fixed in advance), within each role:** best anomaly detector (AE vs IF) and best classifier (XGBoost / RF / LSTM), each by highest binary F1 averaged over Experiments B and C. For C use the **as-trained** score averaged over **both directions** (threshold refit uses target-domain data a deployed system wouldn't have). The two winners deploy as a **pair**; combined latency < 50 ms per window.
- **Experiments:**
  - A time-based split;
  - B leave-one-attack-out: train on A's training sessions with class X removed; test on A's test sessions (normal traffic + class X), so precision and FPR are defined;
  - C cross-dataset (testbed ↔ CICIoMT2024, shared classes and features, explicit label map). Report AE and IF **twice**: as trained, and with only the threshold refit on a small sample of target-domain normal traffic;
  - D **indicative** benchmark on CIC's own feature CSVs + official split (re-extracted-feature version = stretch);
  - E live run of the deployed pair.
- **Metrics:** binary precision/recall/F1 (headline), PR-AUC, ROC-AUC, FPR at fixed recall; macro-F1 for classifiers in A; time to detect; attack-type accuracy; incident-grouping accuracy; share of withheld attacks reaching "possible novel" or "review"; false-novel rate on benign disruptions (reboots, jitter); expected calibration error; SHAP sanity check; training time, latency, CPU/memory. Mean ± std over 5 seeds; **block-bootstrap** CIs for headline comparisons, resampling whole attack runs/sessions, never individual windows (consecutive windows are near-identical; seeds only vary the model).
- **Forensic triage:** group alerts into incidents (target device + source + time gap) with timeline, scope, top contributing features in plain language (TreeSHAP for XGBoost/RF; per-feature reconstruction error for the autoencoder; LSTM explanations computed after the alert, outside the 50 ms scoring path), and a SHA-256-hashed PCAP slice. Calibrate classifier probabilities (isotonic/Platt). Classifier outcome = confident attack / unsure / confident benign (cut-offs set on validation data). Six verdicts:

  | Anomaly detector | Classifier | Verdict |
  |---|---|---|
  | Anomalous | Confident attack | Known attack (type named) |
  | Anomalous | Unsure | Possible novel attack |
  | Anomalous | Confident benign | Detectors disagree → review |
  | Normal | Confident attack | Detectors disagree → review (expected for stolen-credential attacks) |
  | Normal | Unsure | Low priority, logged |
  | Normal | Confident benign | No alert |

  Report how many real attacks land in each cell.
- **Real-time & dashboard:** live 5-second windows → detector pair → incidents → **Streamlit** (port 8501) showing live alerts, model comparison, confusion matrices, calibration plots and SHAP. Grafana is stretch.
- **Analyst walkthrough:** 3–4 incidents traced from alert to timeline, explanation and hashed evidence (illustration, not a user study).
- **Tracking:** MLflow; every number in the report must trace to a logged run.

## Working rules

1. Follow the hard rules in `docs/environment.md` (B1) and stop-and-ask conditions (B2).
2. **Never fake success.** Don't quietly drop an attack, loosen labels, skip a test or simplify a task when something fails. Log it in `docs/REPORT_NOTES.md` and ask if it changes the plan.
3. **Suspiciously good results are bugs until proven otherwise.** Near-100% on experiments B or C → check feature importances for leaked identifiers or timestamps before reporting.
4. Log every decision, success, failure, workaround and metric to `docs/REPORT_NOTES.md` using its template. Never edit past entries.
5. Notebooks are for exploration only; anything that appears in the report comes from scripts in `src/` and is reproducible via the Makefile.
6. Write so the user manual can reproduce everything: one command per step, pinned versions, fixed seeds.
7. Commit after each task with a clear message. Never touch Git history, hooks, remotes or credentials.
